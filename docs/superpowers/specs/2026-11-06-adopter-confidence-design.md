# Proofline adopter-confidence design

## Authorization and intent

The user requested parallel implementation of repository safeguards, self-service onboarding and reliability tracking, complete testing, then an independent review and rating. This increment implements those three workstreams using the existing source-native React/Vite harness. It does not promise a target score or substitute agent tests for human adoption or operating history.

The original portable design and its acceptance criteria remain binding. The previous verified source is `775c62087aa2f443fc409aba750911215ba2aa2e`; local administrative closeout is `1c1d546cb26a3f839eeb9ae7f128e46d3150145d`. Historical records and failures remain unchanged.

## Approach and boundaries

Use small dependency-free Node operational modules alongside the existing portable core, deterministic Vitest regressions, source-controlled policy and concise operator/adopter guides. Extend existing discovery/coverage/ownership metadata rather than introduce another testing framework or backend. The three workstreams have disjoint implementation files; the controller owns shared metadata, integration, remote operations and closeout.

Alternatives considered: documentation alone would leave safeguards procedural and setup error-prone; a hosted control service or npm publication would expand credentials, operation and distribution scope. Source-native CLIs with explicit inputs and fail-closed checks fit this repository and can be independently exercised now.

No live staging, provider contact from tests, npm/tag/GitHub Release publication, support SLA, human pilot, broader browser/platform support or hostile-code sandbox claim is added. The existing presentation remains a dated snapshot. New operational GitHub API calls run outside guarded tests and are recorded separately from offline fixtures.

## B. Self-service onboarding

Provide an explicit source-pinned CLI with a read-only plan as its default. It inventories the reusable core and verifies full commit identity, clean relevant source bytes, paths and SHA-256 hashes. It can create a runnable unrelated work-orders starter in a new external destination, without dependency reuse or downloading/installing anything implicitly. It can plan/install only the reusable core into an existing target without overwriting application code, package files, Git history, manifests, records or existing differing files. Installed files remain byte-identical to the selected source. Receipts identify version/schema/source and files; a receipt never claims target tests passed.

Reject traversal/absolute inventory entries, symlinked source/destination paths, overlapping source/destination, dirty source bytes, nonempty starter destinations, partial/changed installations and untrusted receipt inputs. Validate all conflicts before writing. Use exclusive creation and a temporary staging strategy where possible; interrupted work must remain diagnosable and must not delete preexisting files. No shell interpolation, arbitrary target commands or automatic dependency installation.

Upgrade planning must compare installed hashes against the prior receipt and current source, show added/changed/removed/conflicting files and refuse unsafe writes. An explicit apply may update only unchanged previously installed core; any user edit, metadata ambiguity or unrelated collision aborts before mutation. Preserve target history and append-only evidence. The guide must distinguish a runnable starter from adaptation of an existing app: application routes, roles, providers, tests, ownership and workflows still require target-owned engineering.

Receipts are untrusted data and never authorize writable paths. Recompute the exact prior core path/hash inventory from the receipt's full commit in the selected trusted local source repository, without fetching anything implicitly, then require exact equality. Missing prior source objects or a receipt claiming invented core/app/config/Git/manifest/record paths must fail. Revalidate physical paths and unchanged destination bytes immediately before promotion. Removed core files are reported in the plan; this increment refuses apply when removals exist and leaves manual reviewed removal for a separately authorized migration. An incomplete transaction retains a distinct marker/journal/backups, refuses further apply, and never gets a completed receipt. Final receipt promotion occurs only after all installed bytes are reverified; interruption before or after receipt promotion has explicit recoverable/complete semantics.

Do not infer per-test flake rates from aggregate workflow success or classify a failure as infrastructure without evidence.

Supplementary tracking is never release eligibility or native required-test authority. Unobserved history and small samples are visibly unknown. ## Execution rulings

Parallel implementers may edit only their owned files and may not commit or change shared metadata. The controller integrates and makes small scoped commits, appends factual records, and dispatches task reviews. This preserves the user's explicit parallel-work choice while avoiding shared-index and generated-artifact races. Heavy full suites and builds are serialized; focused tests use unique output locations.

Actual normal PR merge may create a distinct main commit. Report that exact source, verify its actual main jobs, and compare executable input trees with the locally fresh-tested implementation; do not treat distinct hashes as identical. The controller updates the clone-visible active status before implementation and leaves the prior completed milestone intact.
